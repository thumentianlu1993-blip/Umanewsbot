## Context

`add-selection-term-quick-add` 已经把“从文章原文选区创建正式术语”的路径缩短为当前文章页内操作。创建成功后，新的 `TermEntry` 会立即进入术语库，但当前文章已存在的 `translated_title_zh`、`translated_body_zh`、`base_translation_zh`、`body_zh` 或编辑稿不会自动变化。

当前代码已有两个可复用基础：

- `stable.services.terms.apply_term_mappings()` 可以对一段中文/混合文本应用正式术语映射；本 change 不能直接用它做全量替换，而应新增“仅应用指定术语”的受控函数。
- `NewsArticle.apply_translation_result()` 与 `manually_edited_fields` 已经表达“翻译结果可更新机器字段，但不应无条件覆盖人工编辑字段”的边界。

本 change 要把“创建术语”之后的下一步做成受控工作流：工作人员可以通过创建成功后的浮层把新术语应用到当前稿件，也可以继续使用页面级重新翻译入口，但系统不能在无确认的情况下覆盖人工编辑稿。

## Goals / Non-Goals

**Goals:**

- 快速创建术语成功后，在候选详情页和编辑台提供清晰的后续动作。
- 支持轻量“应用新术语”，不调用模型，仅把刚创建的指定术语应用到当前文章已有中文字段。
- 后续动作采用页面上方浮层呈现，工作人员点击即可应用，不再二次确认。
- 支持多标签页并行补术语，避免一个标签页的新术语入口覆盖另一个标签页。
- 保留页面级“重新翻译”能力，沿用现有 `translate_article_task`；该能力不属于术语成功浮层。
- 默认保护人工编辑字段，不无提示覆盖 `manually_edited_fields` 中的发布稿字段。
- 记录操作日志，展示成功/跳过/失败反馈。
- 用测试覆盖 OpenSpec 场景，包括不覆盖人工稿、不自动发布、不自动触发未确认任务。

**Non-Goals:**

- 不做全站批量重翻译或批量重应用术语。
- 不引入新数据库表或迁移。
- 不自动发布文章，不改变公开前台发布过滤规则。
- 不自动接受术语候选池候选，不改变术语候选发现逻辑。
- 不改造翻译 provider 的模型提示策略；重翻译仍使用现有翻译链路。

## Decisions

### 采用显式动作，而不是创建术语后自动覆盖

快速创建术语成功后，页面上方展示一个浮层，文案为：

`术语【日文名（中文名）】已添加，点击此处立即应用到文章中`

其中“点击此处”为可交互项，点击后立即把刚创建的术语应用到当前文章，不再弹出二次确认。

浮层只承载“应用该术语到当前稿”这个动作。重新翻译属于页面级按钮或既有入口，不出现在术语创建成功浮层中；如果候选详情页或编辑台已经有重新翻译按钮，本 change 不新增第二个入口。

实现时必须删除上一版内嵌 follow-up 面板：快速术语表单区域内不得再出现“刚创建术语”面板，也不得出现 `retranslate-created-term-*` 这类绑定到新术语上下文的重新翻译表单或按钮。候选详情页已经存在的页面级“重新翻译”按钮保留在翻译结果区域；编辑台如已有页面级重翻译入口也保持原位，不因为术语成功浮层新增入口。

理由：

- 创建术语是低风险写库动作，覆盖当前稿件是高风险编辑动作，应分开确认。
- 编辑台里工作人员可能正在修改标题/正文；自动覆盖会破坏人工工作。
- 候选详情页和编辑台都能复用同一后端动作，但页面文案可以根据上下文提示风险。
- 入口只在快速创建成功后的下一次页面展示中出现；工作人员刷新页面、离开页面或错过成功反馈后，首版不提供常驻补入口。
- 浮层不会阻塞页面，工作人员仍可继续选区、编辑、滚动、点击其他按钮；这些不离开当前页面的行为不会自动关闭浮层。

浮层消失规则：

- 工作人员点击“点击此处”，提交应用该术语动作后消失。
- 工作人员点击浮层中的关闭 icon 后消失。
- 工作人员在当前页面再次创建新术语并产生新浮层时，旧浮层消失。
- 工作人员关闭页面，或通过真实浏览器导航离开当前页面后，重新打开时不补显示旧浮层。
- 浮层展示 15 秒后自动消失。

“翻页/跳转”如果是浏览器真实导航，页面会重新加载，浮层自然消失；如果是不离开当前页面的点击、选区、滚动或编辑行为，则不影响浮层可见性。

备选方案是创建术语后立即重翻译。该方案虽然最省点击，但会增加模型调用成本，并可能覆盖刚完成的人工校对，不适合首版。

### 轻量应用只处理刚创建术语和当前文章已有中文字段

新增后端 POST 视图，例如 `console-article-apply-created-term`，接收 `article_id`、刚创建的 `term_id` 和安全返回上下文。视图读取当前文章和指定 `TermEntry`，只将该术语的 `source_ja` 与日文别名替换为 `target_zh`，并对这些字段应用：

- 机器翻译字段：`translated_title_zh`、`translated_body_zh`、`translated_summary_zh`
- 基准翻译字段：`base_translation_zh`
- 非人工发布字段：`title_zh`、`body_zh`、`summary_zh`、`push_summary_zh`

默认规则：

- 只替换刚创建术语的日文原词和日文别名；不得把整个正式术语库重新应用到当前文章。
- 替换范围是当前文章整篇相关中文字段，不限于创建术语时选中的原文位置，因为同一术语可能在文章中出现多次。
- 机器翻译字段和基准翻译字段可直接更新，因为它们表达系统生成稿。
- 发布稿字段只有在对应字段未被标记为人工编辑时才更新。
- 如果字段在 `manually_edited_fields` 中，默认跳过并提示“已保护人工编辑字段”。
- 首版不提供强制覆盖人工字段入口；即使后端未来保留 force 参数，本 change 的模板和普通路径不得启用。

备选方案是只更新 `translated_*`，让工作人员手动复制到发布稿。该方案最安全，但不能解决编辑台中“当前稿快速吃到术语”的核心诉求。

另一个备选方案是点击后调用现有 `apply_term_mappings()` 全量重扫正式术语库。该方案实现更省事，但用户心智是“刚建一个新术语，就把这个术语应用到本文”，全量重扫会扩大修改范围并削弱审计解释，因此首版不采用。

### 重翻译继续作为页面级能力走现有任务队列

页面级“重新翻译”按钮仍然派发 `translate_article_task`，不新建任务类型。页面需要区分：

- 浮层“应用该术语到当前稿”：同步、轻量、立即反馈。
- “重新翻译”：异步、可能耗时、更新翻译状态。

理由：

- 现有翻译任务已经处理术语提示、未知马名保护、翻译状态和 `TranslationRun`。
- 不新增任务类型能减少调度和失败恢复复杂度。

### 操作日志记录来源术语和字段结果

术语应用视图应记录：

- 文章 ID
- 触发用户
- 新术语 ID 和日文原词
- 更新字段列表
- 跳过的人工字段列表

页面级重新翻译入口也应记录操作日志，包含文章 ID、触发用户和任务触发结果。若后端请求显式携带来源术语，可附加记录，但浮层不提供重新翻译入口，也不要求为重新翻译补来源术语。

首版可通过 quick-create 成功后的 session/redirect 上下文生成一次性浮层入口，并在 POST hidden `term_id` 传入“刚创建的术语”。后端不能把 `term_id` 当作授权依据；它必须校验文章、用户权限、术语存在且启用，并只把它用于限定替换范围、日志和提示。

由于当前后台只有单一可信操作者使用，首版不增加后端一次性 token 限制：有权限工作人员手工构造 POST 调用指定术语应用接口被视为可接受风险。UI 层仍必须坚持一次性浮层语义。

### 多标签页上下文不能互相覆盖

session 中不得只保存一个全局 quick-term follow-up 槽位。应保存一个 pending follow-up 字典或列表，并使用 nonce 或 `article_id + term_id + source_context` 作为键。

规则：

- 在文章 A 创建术语后，文章 A 的浮层上下文不得被文章 B 的快速创建覆盖。
- 页面渲染时只消费当前文章和当前页面上下文对应的 pending follow-up；如果 session 中存在其他文章或其他页面上下文的 pending follow-up，当前页面不得 `pop` 或删除它。
- 同一页面产生新的快速创建结果时，新浮层替代旧浮层。
- 已展示过的浮层上下文应从 session 中移除，保证关闭页面再打开不会补显示旧浮层。
- 建议 pending 结构保存为按上下文 key 分组的字典，例如 `{"candidate:<article_id>": payload, "editor:<article_id>": payload}`。同 key 写入时覆盖旧 payload，不同 key 之间互不影响。

### 返回路径必须安全

术语应用和页面级重新翻译动作完成后应回到原候选详情页或编辑台，但后端不得信任任意 `next` URL。首版建议使用 `source_context=candidate|editor` 推导返回地址；如果继续接收 `next`，必须只允许站内后台路径，非法值回退到当前文章的候选详情页或编辑台安全默认页。

### 页面反馈以浮层和当前页 messages 为主

快速创建成功后的下一步入口使用浮层。应用动作完成后的结果仍可使用 Django messages。成功提示应包含：

- 已应用该术语的字段数量或字段名。
- 如跳过人工字段，应明确提示哪些字段被保护。
- 页面级重翻译入口如保留在页面其他区域，应提示“已重新触发翻译”，不宣称立即完成。

如果后续需要更流畅体验，可以再做 AJAX 状态组件；首版保持 Django 模板简单可靠。

### 测试必须反向锁定旧交互不会回归

本轮 review 发现旧实现容易被测试固化，因此测试不仅要断言新浮层存在，还要断言旧入口不存在：

- 创建术语成功后页面包含完整浮层文案 `术语【日文名（中文名）】已添加，点击此处立即应用到文章中`。
- 页面不包含快速术语表单内部的“刚创建术语”内嵌面板。
- 页面不包含 `retranslate-created-term-candidate` 或 `retranslate-created-term-editor`。
- 点击浮层中的应用入口提交的是指定术语应用表单，不触发 `translate_article_task`。
- 多标签页测试必须覆盖“打开不匹配文章/上下文不会消费其他 pending follow-up”。

## Risks / Trade-offs

- [Risk] 指定术语应用仍是简单字符串替换，可能在中文稿中替换到不该替换的片段。
  Mitigation: 仅对当前文章、由工作人员显式触发；保留跳过人工字段和操作日志。

- [Risk] 工作人员可能误以为“应用术语”会重新理解日文原文。
  Mitigation: 页面文案区分“应用术语映射”和“重新翻译”；前者不调用模型。

- [Risk] 同步重应用字段较多时可能难以判断变化。
  Mitigation: messages 和日志记录更新字段，必要时后续补 diff 预览。

## Migration Plan

1. 新增指定术语应用服务函数与后台 POST 视图。
2. 在候选详情页和编辑台增加浮层“应用术语到当前稿”入口；页面级“重新翻译”沿用现有入口，如已存在则不新增。
3. 增加视图、服务和模板测试。
4. 执行 `DB_ENGINE=sqlite python manage.py check`。
5. 执行相关 `stable` 测试；必要时执行全量 `DB_ENGINE=sqlite CELERY_TASK_ALWAYS_EAGER=true python manage.py test stable`。
6. 执行 `openspec validate reapply-terms-after-quick-add --strict`。
7. 本 change 无迁移；生产回滚仅需回滚代码。已通过重应用修改的文章字段属于普通内容编辑结果，可在后台人工修改或重新翻译恢复。

## Open Questions

- 首版是否提供“强制覆盖人工字段”按钮：已决定不做。
- 重应用后是否自动重新跑自动化门禁：建议不自动跑，避免隐式改变发布状态；如需要可在后续 change 做。
- 是否需要展示字段级 diff 预览：首版不做，但如果人工担心替换范围，可以作为后续增强。
