## Context

当前仓库已经具备新闻抓取、自动化内容运营、术语候选池、术语库、重点赛事优先级和外部赛马数据导入基础。现有数据结构中，`NewsArticle` 已保存文章标签、自动化分类、区域、语言、发布决策、改写状态和 `decision_reason` 信号；`TermEntry`/`TermAlias` 已能表达赛事术语、别名和 `race_grade`；`ExternalRace`/`ExternalRaceEntry`/`ExternalRaceResult` 已能承接外部赛马数据。

当前缺口是产品层没有“年度赛事页 / 赛事日历”的稳定对象：没有 RaceEvent、RaceCatalog 或 ArticleRaceLink，也没有前台赛事详情页、赛事日历、后台候选确认和人工纠偏工作台。因此本变更新增一个薄的产品层，复用现有新闻与外部数据，不重构新闻主干链路。

## Goals / Non-Goals

**Goals:**

- 以“每年一个赛事页”为粒度，支持 P0/P1 重点赛事的年度赛事详情页。
- 支持赛事日历，按时间展示所有前台可见赛事，并提供“全部 / 重点”、地区筛选、当前日期定位和懒加载。
- 支持赛前、赛中、赛后三种展示状态：赛中只标识进行中，赛果正式确认后再展示赛后结果。
- 支持后台人工维护、CSV 种子导入、指定网站候选抓取、候选对照预览和按模块应用。
- 支持新闻与赛事的自动候选关联和人工纠偏，优先复用 TermEntry、TermAlias、NewsArticle 自动化决策和内容分类。
- 支持赔率、出走状态/退赛状态等动态字段白名单自动更新，但不在赛事日历展示赔率。

**Non-Goals:**

- 不建设完整赛果数据库。
- 不建设马匹数据库、血统库、马匹详情页或马匹历史战绩。
- 不做复杂赛事聚类、跨年度总览页或完整 RaceSeries 前台页。
- 不承诺赛中实时排名、分段进度或直播级数据；本次仅做只读调研任务。
- 不新增独立前端构建系统，不重构 Django 单体、新闻流、自动化发布主链路。

## Decisions

### 0. 交互原型基准

本 change 的前后台交互以 Stitch 项目 `14814699552725196030` 中已确认的 9 张原型屏为实现基准：

- 移动端：`UmaFans 赛事日历`、`UmaFans 赛事详情 - 赛前`、`UmaFans 赛事详情 - 赛后`
- PC 端：`UmaFans 赛事日历 (PC)`、`UmaFans 赛事详情 - 赛前 (PC)`、`UmaFans 赛事详情 - 赛后 (PC)`
- 后台：`UmaFans CMS - 赛事日历管理列表`、`UmaFans CMS - 赛事详情维护 (高级编辑版)`、`UmaFans CMS - 候选资料与关联新闻确认工作台`

实现时应保留这些原型的产品取舍：前台日历高密度展示但不展示赔率；详情页区分赛前、赛中和赛后；后台以候选确认、字段锁定、可见性控制和新闻纠偏为核心，不建设复杂规则 UI。

### 1. 新增产品层 RaceEvent，而不是直接公开 ExternalRace

新增年度赛事产品模型承载公开展示与人工确认状态，建议核心模型为：

- `RaceEvent`：年度赛事主体，字段包括 `year`、`slug`、`original_name`、`chinese_name`、`country_region`、`racecourse`、`grade_text`、`normalized_grade`、`surface`、`distance_text`、`eligibility_text`、`race_datetime`、`timezone`、`priority`、`status`、`is_featured`、`visibility_status`、`data_quality_status`、`source_refs`、`manual_lock_flags`，并可选保存 `major_race_event` 或 `external_race` 引用用于追溯来源。
- `RaceEventAlias`：赛事别名，区分原文、中文、简称、历史名和来源。
- `RaceEventRunner`：出马表/闸位模块，保存马号、马名、骑师、练马师、闸位、负磅、赔率、热门度、出走状态和动态更新时间。
- `RaceEventResult`：赛果模块，保存名次、马号、马名、骑师、练马师、时间、马身差、赔率/热门度回显、闸位/负磅回显、退赛/取消等状态。
- `RaceEventHistoryWinner`：近几年冠军列表，独立于马匹数据库。
- `RaceEventDataCandidate`：指定网站或外部数据形成的候选资料，按模块保存候选值、来源、抓取时间、差异和应用状态。
- `ArticleRaceLink`：赛事与文章关联，保存关联来源、置信度、人工确认/移除状态和关联分组。

选择原因：公开页面需要可见性、人工确认、模块锁定和候选差异，这些是外部数据表不应承担的产品语义。`ExternalRace` 继续作为可选数据来源，RaceEvent 才是前台真实读取对象。现有 `MajorRaceEvent` 保持生产窗口升频用途，不直接承担前台赛事页；如果同一赛事已经存在 `MajorRaceEvent`，可以通过可选引用或导入转换复用其日期、地区和等级，但不得把公开可见性、候选资料和赛果写回 `MajorRaceEvent`。

替代方案：直接扩展 `ExternalRace`。放弃原因是它会混淆“外部原始数据”和“已确认可公开产品资料”，也不利于人工纠偏。

### 1.1. 全球赛事等级与 surface 使用双字段规范化

`RaceEvent` 保存来源原文等级 `grade_text`，同时保存系统可筛选的 `normalized_grade`；`normalized_grade` 优先复用现有 `RaceGrade` 能表达的 G1/G2/G3/Jpn/JG 等值，无法可靠映射时保留原文但不强行塞入日本向枚举。`surface` 使用受控值 `turf`、`dirt`、`jumps`，来源文本和更细节的 going/track condition 保存在扩展字段或原始 payload。

选择原因：MVP 覆盖日本、香港、英国、法国、美国，公开展示必须保留原文等级，同时后台筛选和重点判断需要可比较字段。surface 三值来自产品决策，适合第一版稳定筛选。

替代方案：所有等级都强制使用现有 `RaceGrade`。放弃原因是现有枚举主要服务日本新闻评分，可能无法准确表达所有国际来源的等级文本。

### 2. 年度赛事页是主对象，系列聚合只保留内部字段

URL 使用年度粒度，例如 `/races/2026/takarazuka-kinen/`。可在 `RaceEvent` 中保留 `series_key` 或 `canonical_race_key` 用于历史冠军、别名归并和后台筛选，但第一版不提供独立系列页。

选择原因：用户明确希望每年一个赛事页，且赛前/赛后资料都围绕年度举办实例变化。内部 key 能避免未来做系列页时迁移成本过高。

替代方案：先建 RaceCatalog/RaceSeries，再挂年度 RaceEvent。放弃原因是 MVP 会多一层管理成本，且前台并不需要系列页。

### 3. 资料候选与公开资料分离

人工/CSV 创建的赛事满足名称、日期、马场、等级后可默认前台展示；指定网站抓取出的资料只进入候选/草稿，后台确认后才应用到公开字段。候选按模块分组：基础资料、历史冠军、出马表/闸位、赛果、相关新闻关联。

人工编辑过的结构化模块默认加锁，重抓只提示差异；赔率、出走状态/退赛状态等动态字段作为白名单例外，可自动更新到前台并展示更新时间。

候选抓取、候选应用、动态字段刷新和人工移除关联都应写入可追溯记录：用户触发的后台操作写 `OperationLog`，批处理或管理命令写 `TaskExecutionLog` 或候选状态/错误字段，避免失败只停留在命令行输出中。

选择原因：赛事信息整体稳定，但来源抓取仍可能不完整或格式不一。候选隔离能保护公开页面可信度，也保留人工纠偏能力。

替代方案：抓取后自动覆盖公开资料。放弃原因是风险高，且与“抓取草稿默认不可见”的产品决策冲突。

### 4. 新闻关联分为自动公开、候选和人工移除

关联规则按置信度分层：

- 标题或摘要命中 RaceEvent 正式名/别名，且文章已发布，可自动展示。
- 仅正文命中、仅日期窗口命中、仅 AI/实体识别弱信号命中，进入候选。
- 日期窗口用于降低误关联：赛前、赛后、回顾文章按赛事日期前后窗口筛选。
- 人工移除写入 `ArticleRaceLink`，后续自动任务不得重新展示同一文章与赛事的关联。

选择原因：现有 `NewsArticle` 已有内容分类、标签、术语命中和自动化决策信号，新增关联服务即可复用，不需要改写新闻抓取/发布链路。

替代方案：只用 AI 做赛事识别。放弃原因是不可解释，且会削弱术语库与人工纠偏价值。

### 5. 前台采用 Django 模板，不引入独立前端

赛事日历和赛事详情页继续放在 `server/stable/templates/` 与 `server/stable/static/`。移动端和 PC 共享数据接口/视图，使用响应式模板分化布局：

- 移动端日历：日期分组 + 赛事卡，卡片展示赛事名、马场、出走时间、等级、surface；赛后卡展示前 5 名和马身差。日期和国家/地区通过页面级交互呈现。
- PC 日历：高密度表格，展示日期、时间、状态、赛事、地区/马场、等级、surface、赛前状态或赛后前 5 名摘要。
- 详情页：顶部 Header 根据状态切换；下方 tab 为概览、赛果、新闻、历史。出马表不单独成 tab，归入概览。

选择原因：现有公开站没有独立前端构建系统，MVP 应优先闭环可用，避免新增复杂技术栈。

替代方案：新建前端应用。放弃原因是超出 MVP 且会改变主干架构。

## Risks / Trade-offs

- [候选来源格式不稳定] -> 来源适配器先支持少量指定网站，候选保存原始 payload、抓取时间和解析错误，公开应用必须可回滚到人工值。
- [自动关联误伤] -> 只有标题/摘要正式名或别名命中才自动公开，弱信号进入候选，人工移除设置不可自动恢复。
- [赛事资料缺字段导致页面空洞] -> 前台按模块有数据才展示；后台显示完整度和缺口；最小公开条件仅为名称、日期、马场、等级。
- [前台产品赛事与生产窗口赛事概念混淆] -> `RaceEvent` 只负责公开赛事页和日历，`MajorRaceEvent` 继续负责抓取/发布升频窗口；两者只通过可选引用或导入转换复用基础资料。
- [全球等级映射错误] -> 保存 `grade_text` 原文并单独保存 `normalized_grade`，筛选和 priority 使用规范化值或人工指定 priority，不丢弃来源原文。
- [赔率字段敏感或变化快] -> 第一版只在详情页出马表作为普通动态字段展示，不进入赛事日历，也不作为 Header 或独立模块。
- [懒加载导致当前日期定位不准] -> 以服务端日期窗口分页为主，首屏返回当前日期附近窗口，前端只负责继续加载前后窗口。
- [赛中状态缺实时数据] -> 第一版仅显示“进行中”，并安排只读调研任务记录可行性，不把实时进度作为验收项。

## Migration Plan

1. 新增模型与迁移，不修改现有 NewsArticle 主字段语义。
2. 新增 CSV 导入命令，先导入 P0/P1 年度赛事种子。
3. 新增后台工作台与 Django Admin 表级入口，先完成人工维护闭环。
4. 新增赛事日历和赛事详情页，默认只读取 `visibility_status=published` 的 RaceEvent。
5. 新增候选抓取与关联任务，候选默认不公开。
6. 在 staging 或本地 SQLite 中导入五个代表地区样本并验证前后台闭环。
7. 生产部署时先迁移和导入少量 P0/P1 种子，再逐步开启前台入口。

回滚策略：保留迁移可逆路径；前台入口可通过路由/导航隐藏，RaceEvent 数据不影响原新闻首页；候选抓取任务可停用，新闻发布主链路不受影响。
