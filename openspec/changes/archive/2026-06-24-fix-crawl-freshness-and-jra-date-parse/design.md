## Context

生产排查确认，netkeiba 新着顺在 `2026-06-23 22:00` 之后仍按小时运行，但连续返回 `new=0 seen=120`。这说明候选池没有新增并不等同于抓取任务中断；后台目前缺少把这种状态直接呈现给工作人员的入口。

同一次排查还发现两个独立问题：

- JRA 官方新闻抓取每 12 小时失败一次，错误为 `time data '5月31日' does not match format '%Y年%m月%d日'`。
- netkeiba 访问量榜和注目数榜当前每天只在 `00:00/12:00` 与 `00:05/12:05` 抓取第一页，频率不足以稳定捕捉短时间上榜新闻。

当前实现已经有 `CrawlJob`、`NewsSource.last_crawl_*`、`TaskExecutionLog` 和后台来源列表，可以在不新增主数据模型的前提下改善可观测性。

## Goals / Non-Goals

**Goals:**

- 修复 JRA 无年份日期格式导致的抓取失败。
- 提高 netkeiba 访问量榜和注目数榜抓取频率，降低短时热点遗漏概率。
- 让后台能直接解释每个来源最近一次抓取是否成功、新增多少、重复多少、失败原因是什么。
- 让连续无新稿与连续失败在代码和测试中有稳定判定口径。
- 更新部署与排障文档，记录新的抓取频率和验收命令。

**Non-Goals:**

- 不改变新闻主表的去重键和抓取入库模型。
- 不在本 change 中实现“榜单快照触发高价值重新评分”。
- 不在本 change 中实现“访问量榜/注目数榜历史趋势分析”。
- 不在本 change 中实现新闻编辑页选区加入术语库。
- 不在本 change 中改变自动发布门禁、评分阈值或发布批次策略。

## Decisions

### 榜单频率先配置化到较高频，并同步来源定义

将访问量榜和注目数榜从半天一次调整为更高频的 Celery beat crontab。第一版建议每小时一次，注目数榜与访问量榜错开 5 分钟，保持对上游的请求压力可控。

同时必须更新 `server/stable/services/sources.py` 中的 `BUILTIN_SOURCE_DEFINITIONS`：

- 访问量榜、注目数榜的 `crawl_interval_minutes` 与实际 beat 频率保持一致。
- 备注从“每 12 小时”更新为新的抓取策略。
- `sync_builtin_sources()` 部署后会将该定义同步到生产 `NewsSource`，后台来源列表和异常检测才能使用正确间隔。

备选方案是按白天/夜间设置不同频率，例如白天每 30 分钟、夜间每 2 小时。该方案更精细，但会增加调度可读性和验收成本。第一版先用小时级频率，后续根据命中率再优化。

### 后台展示复用现有 `CrawlJob` 与 `NewsSource.last_crawl_*`

来源健康展示优先复用现有数据：

- `NewsSource.last_crawl_at`
- `NewsSource.last_crawl_status`
- `NewsSource.last_crawl_message`
- 最近一次 `CrawlJob.success_count`
- 最近一次 `CrawlJob.fail_count`
- 最近一次 `CrawlJob.error_message`

这样不需要新增迁移，也能快速回答“任务有没有跑、有没有新增、为什么失败”。如果模板需要展示更丰富状态，可在 view 层组装 `source_health` 结构，不把诊断状态提前固化进数据库。

### JRA 日期解析在 adapter 层兼容

JRA 上游日期属于来源格式问题，应在 `server/stable/adapters/jra.py` 内处理。解析逻辑需要兼容：

- 带年份日期：`2026年5月31日`
- 不带年份日期：`5月31日`
- 月日零填充或不零填充

年份推断规则按信息可信度排序：

1. 列表页日期优先使用 `fetch_listing()` 传入的 `page_or_month` 年份。
2. 详情页日期优先从 URL 路径或来源上下文中提取年份；拿不到时使用当前东京时间年份。
3. 如果按当前年份推断出的日期晚于当前东京日期超过 7 天，则回退到上一年，避免跨年附近误判。
4. 如果仍无法解析，则记录该条异常并按任务策略处理，不静默伪造日期。

JRA 列表中单条日期或详情异常不应直接吞掉整个月份中其他可解析新闻。实现时优先让单条异常记录到任务日志或抓取摘要，并继续处理同一列表中的后续条目；只有列表结构整体不可解析或网络失败时，才让 JRA 抓取任务整体失败。

### 连续无新稿不等于失败

`new=0` 且抓取成功时，系统不应标记来源失败。后台应展示为“成功，无新增，重复 N 条”。真正需要告警或高亮的是：

- 连续失败
- 距离最近成功抓取超过阈值
- 任务长期没有生成 `CrawlJob`

这与上游确实没有新文章的正常情况区分开。

## Risks / Trade-offs

- [Risk] 榜单抓取频率提高会增加对 netkeiba 的请求量。  
  Mitigation: 第一版只抓第一页，小时级频率，访问量榜与注目数榜错开执行；后续如需更高频再单独评估。

- [Risk] 不带年份 JRA 日期在跨年附近可能解析到错误年份。  
  Mitigation: 使用当前年份，并对“解析结果明显在未来”的情况回退上一年；增加覆盖跨年边界的单元测试。

- [Risk] 后台展示过多运维字段会干扰日常运营。  
  Mitigation: 只在来源列表/仪表盘显示摘要，把详细错误保留在展开区或详情字段。

- [Risk] 本 change 不处理榜单快照高价值重评分，用户可能以为提高榜单频率后高价值自动放行就完全生效。  
  Mitigation: 在文档和 change 范围中明确说明，榜单快照驱动重新评分是后续独立 change。

## Migration Plan

1. 本地实现并通过 SQLite 下的 Django check 与 stable 相关测试。
2. 部署前确认生产服务器当前 `HEAD`、容器状态和 `.env`。
3. 代码部署后重启 `beat / worker / web`，确保 Celery beat 重新加载新 crontab。
4. 在生产等待连续两个小时或手动触发后观察 `TaskExecutionLog` / `CrawlJob`，确认 netkeiba 访问量榜和注目数榜均按新频率生成记录且错峰执行。
5. 手动或等待 JRA 抓取任务，确认无年份日期不再导致任务失败。
6. 回滚时恢复上一版本代码并重启 `beat / worker / web`；本 change 默认不新增数据库迁移，回滚风险较低。
