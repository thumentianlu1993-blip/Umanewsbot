## Context

当前后台已有完整的正式术语维护能力：`TermEntryForm`、`validate_term_payload()`、术语列表/新建/编辑页面，以及 `/api/terms/create/`。文章候选详情页和编辑台已经展示原文标题、原文正文、译文和“重新发现术语/重新翻译”入口，但工作人员在原文中发现新术语时，仍需要手动复制文本、离开文章页、进入“新建术语”页再填写。

本 change 的目标是缩短人工补术语路径：在文章上下文中选中原文片段，打开一个轻量创建表单，填写中文译词后直接创建正式术语。后续“保存术语后自动重新应用/重翻译”另开 change，因此本设计只负责创建术语和留痕。

## Goals / Non-Goals

**Goals:**

- 在候选详情页和编辑台的原文区域支持选区快速创建正式术语。
- 默认使用选中的日文文本作为 `source_ja`，管理员只需补中文译词，并可调整术语类型。
- 复用正式术语现有校验，避免快速入口绕过重复检查、比赛等级校验、别名归一化和启用状态规则。
- 创建成功后留在当前文章页面，给出明确反馈，并提供进入术语编辑页的路径。
- 操作日志记录来源文章和创建的术语，便于追踪“这个词为什么被加入术语库”。
- 不新增数据库表和迁移。

**Non-Goals:**

- 不自动重新翻译当前文章。
- 不自动改写当前 `title_zh`、`body_zh`、`base_translation_zh`、`rewrite_body_zh` 或自动发布门禁状态。
- 不做模型自动识别候选词，也不替代现有“术语候选池”。
- 不支持批量从一篇文章连续创建多个术语的复杂工作台模式。
- 不在公开前台暴露该能力。

## Decisions

### 使用文章上下文 POST 视图，而不是直接复用通用术语 API

新增 `console-article-quick-term-create` 一类后台路由，接收 `article_id`、`selected_text`、`term_type`、`target_zh` 和可选 `next`。视图内部构造正式术语 payload 后调用 `validate_term_payload()` 和 `TermEntry.objects.create()`。

理由：

- 普通 POST 能自然复用 Django CSRF、messages、redirect 和现有后台权限模型。
- 文章上下文视图可以写入包含文章 ID/标题的备注和操作日志，这是通用 API 不知道的。
- 出错后可以回到原文章页面，并用 messages 展示错误，不需要引入复杂前端错误状态。

备选方案是直接从页面 JavaScript 调用 `/api/terms/create/`。该方案适合纯 API 后台，但当前运营后台主要是 Django 模板，API 错误展示、重复术语跳转和消息反馈都需要额外前端状态管理。

### 页面交互采用轻量选区弹层，保留无 JS fallback

在候选详情页和编辑台的原文标题与正文展示节点上增加 `data-term-selection-source` 标记。页面脚本监听选区变化和按钮点击：

1. 管理员在带 `data-term-selection-source` 的原文标题或正文容器内选中文本。
2. 页面显示“加入术语库”小按钮，或点击固定按钮时读取当前选区。
3. 如果选区起止点不在原文容器内，则不填入表单；否则弹层/内嵌表单自动填入日文原词。
4. 管理员选择术语类型、填写中文译词后提交。

如果浏览器不支持选区脚本，页面仍显示一个“快速新增术语”表单，管理员可以手工粘贴日文原词。

备选方案是只实现右键菜单。右键体验很顺，但浏览器自定义 context menu 在移动端和部分浏览器上不稳定，也容易遮住原生复制功能。轻量按钮更稳；如果实现成本低，可以同时支持右键作为增强，但不作为唯一入口。

### 默认字段保持保守

快速创建默认值：

- `source_ja`：选中文本裁剪首尾空白后写入。
- `target_zh`：必填，由管理员输入。
- `term_type`：默认 `horse`，因为当前最常见需求是补马名；表单必须允许管理员改为赛事、骑手、马主、固定短语或其他类型。
- `is_active`：`true`。
- `priority`：`0`。
- `race_grade`：空。
- `aliases_ja` / `aliases_zh`：空。
- `notes`：自动追加“从文章 #ID 快速添加：标题”。

默认不猜比赛等级、不自动填别名、不自动提高优先级。虽然默认类型为马名，但管理员保存前必须能看到并修改类型，避免普通词被误写成马名。

### 重复与校验失败优先可解释

`validate_term_payload()` 已经负责 `term_type + source_ja` 的重复校验。快速入口应把这些错误映射为页面消息，并尽量提示同类型同日文原词的现有 `TermEntry` ID，方便管理员后续查找。

如果选区为空、过长、包含明显换行段落或中文译词为空，视图必须拒绝创建并回到当前页面提示原因。选区长度建议限制在 80 个字符以内，避免误选整段文章。

### 与 change3 的边界

创建术语成功后只写入 `TermEntry` 并记录操作日志。当前文章不会自动重翻译，也不会自动改写正文或重新跑自动化。页面可以提示“如需让当前稿件应用新术语，请手动点击重新应用翻译与术语”，但自动联动属于后续 change。

## Risks / Trade-offs

- [Risk] 快速入口降低创建成本，也可能增加误加术语。
  Mitigation: 中文译词必填，类型可调整，默认优先级为 0，并继续使用现有重复/类型校验。

- [Risk] 自定义选区按钮可能在不同浏览器选择行为上不完全一致。
  Mitigation: 保留手动粘贴 fallback 表单；核心能力以后端 POST 为准。

- [Risk] 将备注自动写入来源文章可能覆盖管理员自定义备注。
  Mitigation: 快速表单首版不提供备注输入时，由系统生成备注；如提供备注输入，则追加来源信息而不是覆盖。

- [Risk] 用户可能以为保存术语后当前译文会立刻变化。
  Mitigation: 页面文案明确“仅加入术语库，不会自动重翻译”；change3 再做联动。

## Migration Plan

1. 新增路由、视图、表单/服务封装和模板交互。
2. 本地执行 `DB_ENGINE=sqlite python manage.py check`。
3. 执行相关 `stable` 测试，覆盖创建成功、重复失败、空选区失败、权限限制和页面入口。
4. 浏览器验收候选详情页和编辑台选区创建流程。
5. 生产部署只需发布代码并重启 web；无迁移和 Celery 任务变更。
6. 回滚时恢复代码即可，已创建的术语按普通术语记录处理，可在后台停用或编辑。
