# 美国发布：历史来源检查点换绑修复

## 生产事实与原因

PR #299 已合并（`ec799b3afebbe9af6cec8399bdb9d25cd142a66a`）；原精确提交范围 CI 为 940 项、零跳过，交付核验通过。2026-11-12 发布中已执行 `0084_race_event_division_parent`，但数据事务报 `rebind_checkpoint_orphan` 并整体回滚。四应用恢复到 `332fc540`，旧策略及 QQ 关闭状态保持；美国 153 目标的数据包和自动更新尚未上线。

109 条旧地区登记中，法国 10 场曾用 TRA，后来交接到 Geny。其 30 条 TRA 检查点仍作为历史记录保留，当前有效绑定仅指向 Geny。换绑遍历所有检查点，并要求每条都命中当前绑定，错误地把这批历史记录判为孤立记录。全部 30 条均能在同赛事来源登记中匹配 `source_key + registry_digest`。

原美国整包 PostgreSQL 演练确实覆盖 153 目标、111 场 1071 行、公开页面及恢复，但演练脚本将 `rebind` 置空，未装载这 109 条旧地区控制记录。该证据不能代表旧地区生产换绑已经演练；本次明确补齐，不以原通过结果替代。

## 修复边界

- 只更新当前有效来源绑定对应的检查点。
- 非当前绑定的检查点，仅在同赛事存在来源键及非空 registry 摘要完全匹配的历史来源记录时原样保留；不改其摘要、轮询时间、状态或更新时间，不删除、不重新启用来源。
- 无匹配来源证据仍报 `rebind_checkpoint_orphan`，并将检查提前至 dry-run 返回之前。未知检查点不能通过 dry-run 再在实际写入时才被发现。
- 重复执行返回前同样验证历史检查点证据，未知新增记录不能借 replay 绕过检查。
- 发布失败恢复使用数据库内事务收据：先锁定同包既有赛事，等待正在结束的事务释放锁，再查询是否提交。命令stdout丢失不会漏掉恢复；查询失败则保持调度停止。
- v2 领取仍按当前有效绑定，不会领取保留的旧 TRA 检查点。身份、路由、权限、策略和基线校验保持。
- 原 153 目标、111 场 1071 行赛果、101 个来源时刻及 109 条换绑范围不变；原 manifest SHA256 `7895f3f0b44cceefcdd44465cc1ee441bd1c74bb05098ba5206c841e01f44ff5` 保持。
