# 补齐赛事状态自动更新完整链路：产品方案

## 1. 文档状态

- 变更名称：`complete-race-status-automation-coverage`
- 类型：跨模块产品能力与生产安全变更
- 当前阶段：五项产品决定已于 2026-09-05 由用户定稿（第 1、4 项否决工程建议并改写，见第 8 节），方案已按决定修订，待设计复审后进入实现
- 本轮授权边界：只制定和审核方案，不实现、不部署、不改生产数据
- 方案基线：`origin/main@241bf60f0406401115accd59c6f477883692e816`

## 2. 一句话目标

对于“已经公开、能够被已批准数据源唯一识别”的赛事，系统自动完成：

`发现赛事 -> 确认唯一来源身份 -> 补时间和出马表 -> 按时间更新比赛状态 -> 获取正式赛果 -> 公开赛果 -> 继续观察更正`

任何一步无法确定时都停止写入，并明确告诉运营人员“卡在哪里”，不猜比赛时间、不猜赛果、不覆盖人工锁。

## 3. 为什么现在还不算完整

2026-09-04 的生产只读验收显示：

- event 956 已经完整跑通，说明单场链路本身可用；
- 另外三场法国赛事已经收到正式赛果证据，但仍停留在“待举行”，没有公开赛果；
- 当前生命周期有效名单里只有 event 956；
- 未来赛事盘点共 128 场，128 场都没有进入自动纳管，其中 127 场被误判为“路由有歧义”，1 场存在人工锁；
- 127 场“歧义”不是 127 个独立的数据错误，而是同一条产品规则有问题：主数据源和备用赛果源被当成同等级纳管入口；
- 当前数据源只允许查询“今天、明天”的出马表。远期赛事尚未进入来源开放窗口时，系统没有清楚区分“还没到时间”和“真的出错”。

因此现状是“单场灰度成功”，不是“所有合格赛事能够自动闭环”。

## 4. 用户能得到什么

### 4.1 自动纳管

系统每小时检查未来 30 天的公开赛事，并给每场赛事一个清楚的结论：

- `等待来源开放`：赛事仍较远，当前数据源还不提供它；
- `可以自动跟踪`：已经找到唯一赛事身份，可以进入自动链；
- `已在自动跟踪`：时间、出马表、状态和赛果任务正在按计划运行；
- `需要人工处理`：身份多解、人工锁、来源合同失效或数据冲突；
- `已结束`：正式赛果已发布，更正观察期已结束。

“等待来源开放”是正常等待，不算失败；“需要人工处理”才是阻断。

### 4.2 纳管来源：可信来源先到先得

不为地区指定固定“主纳管数据源”。所有已批准的可信来源都可以竞争一场赛事的首次纳管：

- 每场比赛的纳管权只授予一次：首个在合法来源窗口内给出完整合法响应、且赛事身份唯一匹配的来源获得；
- 同一轮盘点中多个来源同时命中时，按 standing policy 为该地区配置的固定来源顺序（`tiebreak_order`）裁决，结果写入审计，不随机；
- 纳管权粘滞：获得纳管的来源继续负责该场的时间、出马表、状态和正式赛果；其他来源只能把赛果证据送入更正渠道，不能中途接管或直接改写；
- 参与竞争的来源必须具备完整能力（赛时、出马表、赛果）；只有赛果能力的来源不参与纳管竞争，只能作为更正证据来源；
- 获得纳管的来源失效（许可、route、身份或有效期）时，该场回到纳管池按同一规则重新授予，全程留换手审计，不允许无记录静默接管。

这样同一地区有多个来源时，不会再因为“两个同等级入口”把整场赛事判为路由歧义：竞争在时间上先后定论，同轮平局有固定顺序。

首版可信来源范围沿用当前已批准来源：

| 地区 | 可竞争纳管（完整能力） | 仅更正/赛果证据 |
| --- | --- | --- |
| 英国 | The Racing API | Sporting Life |
| 法国 | The Racing API | ZEturf、已导入官方事实 |
| 美国 | The Racing API | Horse Racing Nation |
| 香港 | The Racing API | 已导入官方事实 |
| 日本 JRA / NAR | The Racing API | 已导入官方事实 |
| 爱尔兰 | The Racing API | 暂无 |

当前只有 The Racing API 具备完整能力，因此实践中它通常会赢得纳管；但这是竞争结果而不是指定，后续新增完整能力来源时按同一规则参与竞争。

可信来源整体不可用或不再被许可时，系统停止自动纳管并明确告警；不会把仅赛果能力的来源悄悄升级成纳管来源。

### 4.3 自动更新比赛状态

赛事通过可信来源身份和 standing policy 纳管后，自动获得状态更新资格：

- 到计划开跑时间后：`待举行 -> 进行中`；
- 到计划开跑时间 30 分钟后：`进行中 -> 已结束`；
- 如果系统较晚才纳管，而比赛早已超过 30 分钟：允许直接记录 `待举行 -> 已结束`，并标明“较晚纳管”；
- 不补造一条实际上没有观察到的“进行中”记录；
- 延期、取消、缺少准确时间或存在人工锁时不自动推进。

状态更新仍由现有唯一 lifecycle 协调器执行，不增加第二套状态机。

### 4.4 自动公开正式赛果

只有同时满足下列条件才公开：

1. 来源明确给出正式终态；
2. 赛事身份唯一；
3. 全部实际参赛马都有明确结果或非完赛状态；
4. 没有身份冲突、人工锁和过期任务；
5. 当前赛事仍在有效自动纳管范围内；
6. 结果写入、公开开关和来源许可均有效。

正式赛果、赛事状态、确认时间和公开记录在同一事务内完成，不能出现“状态结束但赛果只写一半”。

### 4.5 自动观察赛果更正

正式赛果发布后继续观察 7 天：

- 内容完全相同：记为正常复核，不重复写入；
- 来源明确给出不同的正式内容或更正标记：新增一版赛果并指向上一版；
- 内容不同但没有合法更正依据：只告警，不改公开赛果。

生产环境不为了验收而伪造一条更正。更正写入分支在隔离 PostgreSQL 中用确定性测试证明；生产只验证自然轮询和无变化时的幂等行为，首个真实更正继续作为上线后的持续验收指标。

### 4.6 阻断必须看得懂

只读审计至少分别报告：

- 未来赛事总数；
- 等待来源开放数量；
- 已找到唯一身份数量；
- 已纳管数量；
- 缺少身份、身份多解、人工锁、来源过期和配置漂移数量；
- 已到比赛时间但状态未更新数量；
- 已收到正式赛果但未公开数量；
- 更正观察中的赛事数量；
- 每个阻断原因对应的 event ID 清单。

所有分类必须数量守恒，不能出现“扫描了 18 场，只解释了 5 场”的情况。

## 5. 产品边界

### 5.1 本期包含

- 将纳管来源机制改为可信来源先到先得（一次性授予、固定平局顺序、授予后粘滞、仅完整能力来源可竞争）；
- 修正未来赛事盘点与身份发现的分类；
- 让 standing policy 纳管的赛事自动获得 lifecycle 资格；
- 统一生命周期写入、赛果写入和公开读取的授权判断；
- 为当前已纳管但停滞的赛事提供单独审计修复路径（不等新链自然恢复）；
- 补齐 correction、失败关闭、并发和公开页面测试；
- 更新只读审计、上线步骤和回滚说明。

### 5.2 本期不包含

- 不新增或购买新的第三方数据源；
- 不承诺在来源开放前就获得远期赛时和出马表；当前 The Racing API 入口只覆盖今天和明天；
- 不用模糊赛名、仅日期或仅马场自动绑定赛事；
- 不自动清除人工锁；
- 不批量修改历史赛事状态；
- 不在审计修复包之外手工写赛果或伪造更正；
- 不触碰、消费、迁移或删除旧 `race_live` 队列；
- 不涉及 France 2023 马匹 External staging、马匹身份合并或资料公开；
- 不改新闻、QQ 推送和历史赛事回填链路；
- 不在公开页面显示 provider、provisional、official 等内部术语。

## 6. 关键业务规则

### 6.1 “完整链路”的分母

完整链路的验收分母是：

> 公开、状态允许、没有人工锁、进入已批准来源开放窗口，并能由任一可信来源唯一识别的赛事。

尚未进入来源开放窗口的赛事单独统计为正常等待；来源开放后仍找不到或无法唯一匹配的赛事才计入阻断。

### 6.2 两类 lifecycle 授权不能混用

- 旧的固定 lifecycle registry 继续服务既有手工/固定名单赛事；
- 新的 data-sync 赛事使用 standing policy + enrollment 证据；
- 同一场未结束赛事如果同时命中两类授权，系统必须拒绝写入并告警；
- event 956 已经结束，保留原来的完整证据，不为了新方案改写历史。

### 6.3 已停滞赛事的单独审计修复

event 755、756、757 等已有正式 observation/revision、但状态和公开投影未完成的赛事，不等待新版本上线后的自然 provider 轮询，也不直接投影旧 revision。

系统使用一份独立的“最近 7 天未闭环清单”找到它们。这份清单只包含已经 data-sync 纳管、tracking 仍开启，并且存在未公开正式 revision、开放 incident 或未结束 correction watch 的赛事；它不会扫描或批改全部历史赛事。

对清单内赛事执行一次性审计修复：

1. 重新核对来源证据：以现有 official observation/revision 为基础，对照来源原文或新鲜 provider 响应复核身份、终态和完整参赛名单；
2. 生成 SHA 锁定的不可变候选包，dry-run 确认零写入；
3. 备份并取得人工批准后，在同一事务内写入状态、赛果与公开记录；
4. 独立 verifier 逐场核对数据库与公网页面；
5. 全程记录为人工修复（OperationLog），新链上线后由 standing policy 接管后续更正观察。

前提：修复窗口内没有自动化任务触碰目标赛事（当前定时赛果复核任务已停止）。修复是独立运维操作，不依赖本变更上线；代码不硬编码 event ID，同形态停滞赛事复用同一流程。

standing policy 对状态分成两组：新纳管只接受 `scheduled/postponed`；已经合法纳管的赛事可在 `scheduled/running/finished/postponed` 中继续跟踪。这样赛事进入进行中或已结束后不会反而失去赛果和更正资格。

### 6.4 手工锁永远优先

人工锁只允许人工处理。自动任务只报告锁定字段和 event ID，不清锁、不覆盖字段、不尝试绕过。

## 7. 验收标准

### 7.1 发现与纳管

- 未来 30 天公开赛事 100% 被归入一个明确分类；
- 同地区存在多个可信来源时，不再产生 `standing_policy_route_ambiguous`（先到先得授予 + 固定平局顺序）；
- 进入可信来源开放窗口且可唯一匹配的赛事，在 60 分钟内完成身份建立和纳管；
- 远期赛事明确显示 `awaiting_source_window`，不计作系统故障；
- 人工锁、身份多解、来源过期和合同漂移均保持零业务写入。

### 7.2 时间、出马表和状态

- 来源首次提供准确赛时后 60 分钟内写入；临赛窗口继续沿用现有动态频率；
- 出马表首次完整可用后 15 分钟内更新；
- `待举行 -> 进行中` 和 `进行中 -> 已结束` 的 P95 延迟不超过 5 分钟；
- 延期、取消、缺时间和较晚纳管分支都有明确记录；
- 状态机无重复 transition、无伪造 transition、无跨 event 写入。

### 7.3 赛果与公开

- 上游正式终态被识别后，公开延迟 P95 不超过 5 分钟、P99 不超过 10 分钟；
- 初始观察期内，可被独立证明 T+30 已有完整正式赛果的赛事，确认与公开成功率至少 95%；稳定后至少 99%；
- 错误赛果、部分赛果公开、人工锁覆盖、重复 current revision 和无证据公开均为 0；
- root/www 页面内容一致，统一显示“赛果”，不泄露内部来源和阶段。

### 7.4 安全与资源

- deployment lock、exact image/revision、migration leaf、服务 restart/OOM、内存、Swap、磁盘和三队列全部通过；
- `race_live` 数量在整个发布和验收过程中保持原值；
- 任一关键门禁失败时，在一个 selector 周期内停止新派发和新写入；
- 发布前磁盘必须同时容纳新备份、新镜像和运行增长，并在完成这些动作后仍高于现有 8 GiB 硬门槛。
