# 第4项：P02受保护执行器与隔离演练

本轮沿用已审核的[升级设计](design.md)与[恢复流程](rollout.md)，新增独立P02执行器，不改旧0078/0079的迁移摘要、完成凭据或恢复入口。只在隔离环境实施和验证；生产交付按根[AGENTS.md](../../../AGENTS.md)。

## 实施顺序

1. (operations) 先验证精确候选、数据库、迁移文件、recorder和catalog拒绝条件，再实现共享合同与逐迁移执行入口。每次只提交精确计划的下一项；提交前持久化step intent，提交后持久化receipt。崩溃后只接受同intent已提交的连续前缀，最多补签一个已有step intent且catalog吻合的提交。
2. (operations) 先验证并发、残留writer、备份篡改和中断切点，再实现宿主协调器。初始intent先于停服；备份及完整隔离恢复先于DDL；完成凭据先于正常服务恢复，服务恢复另有回执。所有异常保持可诊断的关闭态，不自动启用P02。
3. (operations) 用独立PostgreSQL 16执行实际DDL、pg_dump/pg_restore、约束与触发器篡改、锁等待和故障续跑；以真实Docker环境验证固定镜像、关闭配置、进程与挂载边界。测试不访问生产、Redis业务队列或第三方来源。
4. (operations) 独立只读review、修复复验，再集中提交和验证所需影响范围。没有新修改/失败/明确风险时不重复已通过测试。

## 固定合同

- 起点只接受精确0079，目标只接受0086；六步顺序不变，不支持逆迁移或自动回退旧镜像。
- 迁移文件摘要固定在代码中；catalog从隔离PostgreSQL实测并经审核冻结，运行时不得从目标数据库生成自己的期望值。
- 所有应用recorder及完整public schema一并检查，不能只检查stable叶。数据库身份包含实际集群及数据库身份，不能仅凭同名DSN。
- intent绑定commit、镜像ID、数据库身份、配置摘要、恢复材料及唯一备份位置。备份回执反向绑定intent；closed handoff绑定二者。文件采用私有权限、无符号链接、原子且不覆盖写入。
- 迁移单一owner持有数据库会话锁；宿主锁须与旧发布入口互斥，并在owner退出后自动释放。不得直接复用无存活证明的裸锁文件。
- 每步执行前重新核对writer关闭、身份、原始材料、recorder/catalog和预算；锁等待5秒、语句120秒。不能因失败而自动扩大预算。
- 新P02 write/delivery关闭、cohort为空；正常服务恢复必须恢复原服务集合及获准配置。只读探针不能消费队列，不能调用业务源或生成公开版本。
- 备份应包含数据库、角色权限、配置、静态/媒体恢复面和旧镜像身份；完整恢复成功、catalog和数据核对成功才生成备份证明。TOC成功不等于恢复成功。

## 证据边界与测试策略

`f05ed604`现有完整CI和目录外交付收据作为基线。开发使用针对性RED/GREEN和发布合同回归，不在每个子步骤重跑全量。当前PR相对main含模型、迁移和配置高风险路径；最终是否要求full由实际影响计划确定，不能把基线收据当成新head验证，也不修改测试规则来规避选集。

空库、合成数据量演练和生产形状副本分别报告。没有足够的生产形状/资源实测时保持发布阻断，不将隔离成功外推为生产停写时限或恢复RTO。来源准入、目标冻结、真实赛日和七天观察仍是独立未完成项。
