## 热点一：网页术语匹配

首次数据库活动采样抓到2个Web术语查询及2个并行worker，持续时间约0.94/1.48秒；随后6次采样中3次再次抓到术语主表/别名查询及并行worker，1次抓到赛事表查询，2次无活动。查询主要处于执行状态，未发现锁等待证据；一次赛事查询主进程处于IPC等待并行worker。

运行代码`StrictRaceTermResolver.resolve()`按页面涉及的名称拼接大量`UPPER(source_ja)=UPPER(value) OR ...`及别名条件。表规模的catalog估计约为术语58211行、别名39063行（统计视图另报别名39926行）；不能将估计当精确行数。术语和别名现有索引不包含对应的UPPER名称表达式。

使用运行容器内ORM、正确地区枚举、1/30个合成名称做**仅EXPLAIN、不执行SELECT**的规划检查：

- 单名称术语查询可选择顺序扫描。
- 30名称术语查询选择并行Bitmap Heap Scan，现有地区/语言/类型索引预计先选出约39640行，再做名称过滤及默认排序。
- 30名称别名查询选择术语及别名顺序扫描和Hash Join，再排序。
- 两次统计快照间，别名索引扫描增加362376次；这是全库并发工作累计，不能全部归因于一个请求，但与低效关联访问的方向一致。

采样SQL因`track_activity_query_size=1024`截断，EXPLAIN用的是同代码结构的合成输入，并非捕获SQL的完整重放；没有运行生产EXPLAIN ANALYZE或压测。已确认热点和缺少直接匹配索引，尚未测出优化后的真实收益。

建议先保持大小写、Unicode、地区/语言、同名冲突与正式中文名规则不变，改进批量查询表达式、移除无用排序，并在隔离PostgreSQL验证表达式索引。不能用Python大小写转换悄悄替换数据库原有语义，也不能以缓存掩盖中文名更新或冲突。页面结果预取量与赛事日期/游标查询列为第二轮优化，暂不重写公开分页行为。

## 热点二：QQ投递无效重试

读取按主键倒序的最近2000条任务日志，并筛选最近10分钟：1965条为`qq_push_delivery`，均记录`retry scheduled: send_failed`；实际覆盖约10:54:16至11:03:02。任务日志虽标success，但其含义是重新安排了任务，不是消息发送成功。

进一步按这些日志的delivery关联只读聚合：

- 187条投递，全部`retrying`、`attempt_count=0`、`max_attempts=3`。
- 全部没有`last_attempt_at`；错误均匹配连接拒绝类别。
- 每条在该有界窗口执行10–20次，合计1965次。

运行代码的确定路径：`process_qq_push_delivery()`先调用`pusher.is_online()`；连接失败后直接`_set_delivery_failure()`；增加attempt_count的`_claim_delivery_attempt()`尚未发生。外层任务发现`retrying`且0<3，于是按`_qq_push_retry_countdown(0)=30`秒再次安排。次数不增加，3次上限无法让这个分支结束。每轮仍会读取投递与文章、检查资格、生成消息、查询目标最近投递时间、检查连接、写状态和日志。

这证明无效重试循环存在；普通worker的瞬时高CPU与大量重试并存，但没有进程级CPU profile，不能断言worker的全部CPU都由它造成。也没有修改连接地址或恢复QQ登录，因为可能恢复真实外部发送，不能夹带进诊断。

优先修复离线重试的有限次数/退避与去重；保留已有发送成功事实和并发claim约束，不能简单前移claim导致离线检查后错误计次或重复发送。当前main已有QQ通道关闭控制，但普通连接失败路径仍在增加attempt_count前返回；不能将未部署的通道控制视为线上循环已经解决。

## 推荐实施顺序与验收

1. QQ无效重试：用隔离测试复现“187条待投递、连接持续拒绝”，验证任务数有界、次数/退避推进、并发不重复发送、既有sent记录不重发。保持外部发送禁用，实际生产开关/队列动作绑定另行精确发布包。
2. 术语查询：以生产规模的合成数据比较SQL计划、行读取、查询耗时；覆盖地区/语言/大小写/别名/冲突语义。先减少重复运算，再验证必要索引；不直接在当前生产执行DDL。
3. 在获准发布后复测同类请求下的DB/worker CPU、负载、任务重试数量及页面延迟。现有诊断没有每个查询的精确CPU占比，也没有优化前后的对照结果。
4. 负载稳定后按既定条件重新安排P02备份窗口。本轮没有协调暂停P04，也没有新备份。
