## 容量计算口径

对每个真实host，逐小时取整个追踪窗口的峰值，不用每天开赛数替代并发库存。重点发现上限60秒，常规120秒；重点未知的25场不得直接按常规计算，补证前压力分析按60秒且仍阻断；没有合格版本索引时full-fetch。名单和赛果两条仍同时有效的链分别计费，跨host请求分别入账；共享批量请求仅在实证可复用时去重。GB/IE/US共用Sporting Life时必须聚合，主备来源都要有自身切换额度。

`base_h = discovery_h + changed_full_fetch_h + recheck_h + retry_h + other_consumers_h`

`required_limit_h = ceil(max_hour(base_h) / 0.70)`

- full-fetch发现包含本次完整读取，不能再将同一请求重复记changed；轻量索引则需额外计变化后的完整读取，变化量未知时不可记0。
- 每条完整链成本按实际请求host拆分：索引/寻址、分页、名单配对、元数据、失败重试均单计。仅有一场成功链不构成全区最大页数上限。
- 复查：确认首24小时每15分钟（4次/小时），第2–7天每日一次；未确认超期首24小时每10分钟（6次/小时），之后每日一次。每日一次仍需计算实际集中执行小时的峰值，不能只用1/24稀释峰值。
- 首次确认后7×24小时持续及时发现，更正不重置起点；未确认库存不按7天自动退出，取消或义务解除必须保留证据。
- 重试次数、退避、429 Retry-After、并发、同host其他消费者、带宽、CPU和排队实测均待冻结。30%余量不替代显式重试/备用成本。不以增加额度或延长SLA解决容量不足。

现有 `source_capacity_report()` 每场使用 `requests × (60或30 + 4)`。其固定+4不能独立证明未确认首24小时的每小时6次复查、多个同时有效模块、寻址及重试等完整成本。**当前命令即使输出ready，也不能解除本报告阻断**；本轮不伪造proof/额度运行出绿色报告，也不改业务代码。进入生产容量准入前需补齐执行合同与拒绝测试。
