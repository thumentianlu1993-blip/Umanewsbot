# 赛事区修复计划

状态：待审阅，仅计划；尚未开始应用实现、数据修复或部署。

## 目标与取舍

基于 [9 月 17 日排查](../../reports/2026-09-17-race-section-audit.md)，先解决四件事：当天有结果却不能正式发布、指定赛事漏配、日本两场 G2 缺资料、过期赛事仍显示赛前。

沿用 `codex/audit-race-section-20260917`。9 月 17 日快照中的生产为 `9a88243f`，79 场是当时的异常数量；实施前重查，不能把快照直接作为写入名单。

本轮采用现有 Django、Celery、候选导入、来源身份、observation/revision 和审计修复机制。**预期不新增表、不新增队列、不引入通用工作流或来源框架。** 如果验证发现必须迁移，先解释现有字段不能解决的具体问题，再调整计划。

交付只分两部分：**一份代码 PR＋一个绑定明确赛事名单的数据修复包**。数据包可以先处理紧急赛事，再按地区分批完成历史记录，不为每个问题另建系统。

## 一、修复当天正式赛果确认

### 最小方案

在现有 TRA 同步入口补充**同日按精确 race ID 查询详情的回退**，复用已有 `/v1/results/{race_id}` 路由、预算、检查点和发布函数。本轮不同时实现赛卡与赛果跨接口拼接确认。

- 当天列表先照常查询。只有已取到本场结果、缺少正式性证据、且尚未确认时，才允许本次执行最多补查一次该 race ID；后续沿用现有退避，不增加轮询频率或请求总额度。
- 缺省状态不得补成 `complete` 或 `official`。保留实际来源状态、endpoint 和证据，分别处理暂定与正式结果。
- 实施第一步核对已有详情响应及接口合同：只有接口自身的明确终态，或可验证的“此接口只返回正式结果”合同，才能提供正式性证据；HTTP 200、有名次、赛卡的 `result`、开赛超过 30 分钟均不单独充当证明。证据复用现有 provenance，不新造通用权威性体系。
- 仍执行精确赛事身份、完整参赛名单／退赛状态、人工锁、获胜来源、claim 和 correction 校验，再走现有正式发布函数。
- 无正式性证据、404、超时或额度不足：保留暂定结果和下一次轮询，记录明确原因。**若详情接口的正式性也无法证明，这项自动确认保持阻塞；不能用注入状态交差。** 其他修复可继续，现有审计补果流程可处理有独立正式证据的目标。
- 历史 observation/revision 不改写；新证据生成或提升版本必须复用现有可审计路径。正式结果不因新空字段降级；重复响应不重复发布。

主要文件：`race_data_sync_providers.py`、`race_data_sync_results.py`；仅在确有需要时改现有 provider 合同配置。同期核对过去 1～7 天路径的默认 `official`，统一使用可追溯的正式性判断，避免当天／次日口径矛盾。

验收：828／830 的 7／5 行缓存重放先复现问题；有正式证据后能在同一天公开，没有正式证据则保持未确认且原因可见。不能以“最终次日补上”证明当天问题解决。

## 二、补齐指定赛事，避免引入新的自动来源

### 尚布利 829

- 对照原始来源修正 `CHAMBL Y` 为 `CHAMBLY`，补精确别名，保留修改前值和证据。
- 日期、地区、马场、比赛身份唯一匹配后绑定来源。保持 slug／公开 URL 不变，不全局删除名称空格，不启用模糊合并。
- 写入时若已错过 today/tomorrow，走显式目标的审计修复，不能期待未来发现自动补回；复用缓存中的赛时、7 匹名单与正式性另行核实的赛果。
- 同批 PDF 的疑似断词只输出待核对清单；未经证据确认的不批量改。

### 日本 104／105

- 本轮先补这两场的 JRA 官方赛时和已公布名单，使用明确官方 URL、日期／马场／赛事核验，不新增全量 JRA 抓取器、provider 竞争路线或周期任务。
- 复用 `RaceEventDataCandidate` 的 BASIC／RUNNERS 和现有审核应用能力；所需准备工具限定显式 event ID 与 URL。现有批量详情 importer 不支持 BASIC，不能假设它可直接写赛时；只补必要的小入口或复用后台已有 BASIC 应用。
- 有名单但未编马号：马号／枠位为空，显示“参赛名单，马号待公布”；最终编号公布后按同一候选流程更新，不能以行号伪造马号。未公布的赔率等字段保持空。
- 仅对未被自动 writer 接管、无冲突人工锁的对象应用；应用时事务内重查。已由 data-sync 管理的赛事不得直接调用旧候选覆盖入口。
- 旧 RUNNERS 应用会整表替换，实施必须测试重复候选、后续编号更新和 TRA 首次纳管衔接：已有来源身份／participant 关系不能丢、不能产生两套重复选手。不通过就不发布该导入能力；不以名字相似跨来源自动合并。复用已有身份校验，缺映射的具体马匹进入待核对。
- 这属于明确的赛前人工补齐，**不把 JRA 提升为自动纳管来源，也不改变已有“先到先得、授予后粘滞”的规则**。

验收：官方资料仍有效时，两场详情可见北京 14:45／日本 15:45、实际名单与编号阶段；重复应用无重复行。若执行时比赛已开始，重新按当前资料阶段准备，不能回填过期赛前快照。

长期日本提前自动同步不在本轮完成声明内；这次保留可复用的候选准备方式，后续有明确需求再接常态调度。

## 三、修正展示与筛选，再回补历史数据

### 展示小修

复用现有 view helper，列表、详情页标题和基础资料区使用同一展示规则；不增加数据库状态枚举，不凭时间写入正式赛果。

| 已有事实 | 对外显示 |
| --- | --- |
| 有通过现有公开门禁的正式赛果 | 已完赛，可查看赛果 |
| 原状态 finished，但正式赛果缺失 | 赛果待确认 |
| scheduled/running 且已超过计划开赛 30 分钟，或无赛时且举办地日期已过 | 赛期已过，资料待补 |
| 取消／延期 | 保留取消／延期，不被日期兜底覆盖 |
| 没有收录出马表 | 本站暂未收录出马表 |

- “即将开赛”不再仅按 status 筛选：有精确赛时的 scheduled 必须尚未到点；无赛时的 scheduled 以举办地日期判断尚未过期；running 和无新赛期的 postponed 不归入“即将开赛”。全部时间仍可找到它们。
- “已完赛”只纳入符合现有公开赛果门禁、可查看正式结果的赛事；SQL 筛选和渲染共用判定，不逐条查库，不只检查存在一行旧 confirmed 结果。
- 直接修正时间歧义：有 datetime 时显示北京时间，并附当地时间／时区；仅有当地日期时显示“当地日期，开赛时间待补”。日历本轮继续按举办地日期分组并明确标注；不改全年翻页、游标和全站跨日分组规则。详情相对日期按赛事当地日期计算。
- 出马表缺失不推断官网未公布；无有效闸位的 `0` 显示“—”。

主要文件：`views.py`、`race_calendar.html`、`race_detail.html` 及实际复用这些信息的首页模板。不给无关页面换版式。

### 历史回补

- 重查 2026-08-16～09-13 的同口径公开异常，冻结实际 event IDs、字段基线和源证据；79 是排查快照，不要求执行时凑够 79。
- 复用现有 recovery inventory、apply/verifier 和区域来源工具。先处理能从现有缓存、结果候选完成核验的记录，再按地区补有明确缺口的来源；不从 1984 年重抓，也不把未来发现窗口扩大成长期历史扫描。
- 每场归入“正式结果已补齐／来源证实取消或改期／仍缺证据”之一。缺证据显示资料待补并列明原因，不能批量将 scheduled 改 finished。
- 自动化已接管的对象走现有 data-sync 审计修复；尚未纳管的对象使用对应人工 recovery 路径。不得通过移除 owner／锁来强行应用。
- 明确区分“过期赛前展示已消除”和“历史赛果已补齐数量”。不能把有缺口的批次说成全量完成。

## 四、最小可观测性

只扩展现有 `audit_race_data_sync` 的有界输出：过期未纳管、未来七天缺赛时／名单、已有暂定但缺正式证据、来源匹配失败。每类给数量、有限 event IDs、最近检查时间和原因。

复用现有 incident／后台查看入口；有暂定结果时记录“缺正式证据”，不再用笼统的 complete 掩盖业务未完成。本轮不建新看板、不新增邮件／QQ／定时提醒渠道，不改变预算分配策略。9 月 10～12 日预算耗尽作为后续独立问题保留。

- 应用发布预期无迁移，复用当前发布协调器；可能重建 Web／worker／Beat／v2 worker，具体服务和配置差异在最终发布包列明。代码、供应商同日补查范围、数据包 SHA、备份与验收一并交付，不在这份计划里假定已批准上线。

- 逐目标核对自动任务／claim 和字段基线；无并发写入窗口后才应用。对初始 5 场和历史批次分别记录数据库与真实公开页验收。普通／v2 队列健康与业务结果分别验收，旧 race_live 不消费。
