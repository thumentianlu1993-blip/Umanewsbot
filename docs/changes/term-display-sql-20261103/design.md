# 网页中文名称查询成本优化

## 范围与基线

用户要求优化网页查中文名称的SQL成本。以主线`6a42c26482fd211a6e20238ec92808c6b4ed77f7`为开发基线，当前生产为QQ恢复窄候选`9def4a7b`；两者`race_term_display.py`一致。生产已开启`RACE_INFORMATION_NORMALIZED_DISPLAY_ENABLED`，严格解析器覆盖网页赛事、马场、马匹、骑师和练马师名称。

本轮只改严格解析器的查询构造，不改名称来源、身份匹配、地区/语言优先级、冲突保留原名、全局回退、未翻译值及开关语义；不动legacy路径，不引入缓存、索引、迁移、配置或数据回填。人工边界统一引用根AGENTS.md；当前工作不含合并或发布。

## 已核实的成本来源

生产只读统计显示术语主表约58211条（马匹52605），别名39926条。现有索引为地区/语言/类型、别名语言/文本及term外键等，没有大小写表达式索引。未启用pg_stat_statements，因此不把累计表扫描次数解释为本次网页SQL实测耗时。

严格解析器按每个输入变体生成`iexact`，PostgreSQL编译为逐项`UPPER(column)=UPPER(value)`的OR链；每类名称两条SQL，仍会随名称数增加大量比较和计划节点，并沿用模型默认排序。200个生产名称的只读EXPLAIN（未执行ANALYZE）显示：主表估算成本11548.99、别名14859.91；候选批量SQL为3481.71、4800.49。估算不等于生产实际提速。

## 改写原则

- 保留现有输入变体：原名strip与NFKC后压缩空白的形式。
- 使用数据库两端`Upper`及`IN`批量匹配；不能在Python提前upper/casefold右值替代数据库排序规则，以免Unicode大小写召回发生变化。
- 候选查询取消默认排序。解析仍按实体ID去重、保留冲突；同一实体的主名/别名共享目标中文名和地区，所以结果不依赖候选顺序。
- ORM参数绑定保留，百分号、下划线、反斜杠和引号仍按名称字面值处理。
- 不用只减少SQL条数作为性能证据；在隔离PostgreSQL用合成近似规模数据比较旧/新SQL的结果集合、EXPLAIN ANALYZE与实际耗时。

## 验证

已取得真实RED：200个不同名称的解析仍展开OR并默认排序，新增查询形状契约失败。后续覆盖主名/别名冲突、同实体去重、地区/语言/类型分离、未翻译、NFKC/空白及数据库Unicode大小写等价性。既有40赛事/200参赛者至多10条查询的页面合同继续保持。生产仅做有界只读计划诊断；自动测试不得访问生产或第三方。
