# 赛马新闻系统 V1 上线准备 PRD（Codex 执行版）

## 1. 文档目的

本文档用于指导 Codex 完成当前赛马新闻系统在生产环境上线前所需的工程化与部署准备工作。

本轮目标不是新增业务功能，而是把现有系统从“本地开发可运行”推进到“云端生产可部署、可访问、可监控、可恢复”。

---

## 2. 当前项目现状

当前系统已经具备以下业务能力：

1. 已完成 `netkeiba` 和 `JRA` 两个来源接入
2. 已完成新闻、图片、榜单快照、来源、抓取任务、媒体素材、操作日志等模型
3. 已完成后台登录、工作台、来源管理、候选新闻池、三栏编辑台、已发布内容管理、操作日志
4. 已完成前台首页和文章详情页
5. 已完成术语映射、翻译接口封装、QQ 推送模块
6. 已完成历史数据回填
7. 已修复正文解析时内联专有名词被错误拆行的问题

因此，本轮不再以“开发新产品功能”为核心，而是聚焦上线前的工程准备。

---

## 3. 上线方案（已拍板）

本轮上线方案固定如下，Codex 不需要再做技术路线选择题：

### 3.1 云环境
- 云厂商：阿里云
- 地域：香港

### 3.2 运行架构
- 1 台 ECS 运行应用层
- 1 个 RDS PostgreSQL 作为数据库
- 1 个 OSS 作为媒体与图片存储
- 前台与后台共用一个域名：
  - 前台：`https://your-domain/`
  - 后台：`https://your-domain/admin/`

### 3.3 应用运行组件
ECS 上运行：
- Django Web
- Celery Worker
- Celery Beat
- Redis
- OneBot / QQ 推送服务
- Nginx

### 3.4 媒体资源策略
- 图片、封面图、本地化媒体资源，不放本机长期存储
- 所有正式媒体资源应存储到 OSS
- 数据库记录媒体元数据与访问 URL

### 3.5 部署方式
- 使用 Docker Compose 部署生产环境
- 不单独做云上 staging 环境
- 本地测试通过后，直接部署到香港生产环境

## 7. 详细需求

# 7.1 生产部署结构

## 目标
让整个系统可以在香港 ECS 上通过 Docker Compose 稳定启动。

## 要求
需要提供生产环境部署文件，至少包含：

- `docker-compose.prod.yml`
- `.env.example`
- `Dockerfile`（如已有则检查生产可用性）
- Nginx 配置文件
- 启动说明文档
- 部署脚本（如 `deploy.sh`）

## 运行服务
`docker-compose.prod.yml` 至少应包含以下服务：

- `web`
- `worker`
- `beat`
- `redis`
- `nginx`
- `onebot`（若当前项目内已集成则按现有结构处理）

说明：
- 数据库不在 Compose 内自建，使用外部 RDS
- 图片不长期保存在本地容器文件系统

## 验收标准
- `docker compose -f docker-compose.prod.yml up -d` 后，服务可正常启动
- 服务重启后仍可恢复运行
- 依赖顺序合理，避免启动时数据库或 Redis 未就绪导致应用异常退出

---

# 7.2 Django 生产配置

## 目标
让 Django 从开发模式切换为正式生产模式。

## 要求
必须完成以下生产配置检查：

1. `DEBUG = False`
2. 正确配置 `ALLOWED_HOSTS`
3. 正确配置 `CSRF_TRUSTED_ORIGINS`
4. 通过环境变量注入 `SECRET_KEY`
5. Session / Cookie 走安全配置
6. 正确处理 HTTPS 反向代理头
7. 正确配置静态文件收集
8. 正确配置日志输出
9. 自定义 404 / 500 页面（如实现成本低可完成）

## 环境变量
所有敏感信息必须走环境变量，不允许硬编码进仓库：

- Django `SECRET_KEY`
- 数据库连接信息
- Redis 连接信息
- 翻译 API Key
- OSS Key
- OneBot / QQ 推送配置

## 验收标准
- 生产环境中不再使用开发配置
- 后台与前台都能正常访问
- 关键配置通过 `.env` 或其他环境注入方式管理

---

# 7.3 RDS PostgreSQL 接入

## 目标
将数据库切换为阿里云 RDS PostgreSQL。

## 要求
1. 使用外部 RDS 作为正式数据库
2. 提供数据库连接配置示例
3. 支持执行迁移
4. 支持导入已有数据
5. 检查连接超时、字符编码、时区设置

## 不要做的事
- 不要在生产 Compose 中继续使用本机 Postgres 容器作为正式数据库

## 验收标准
- 生产环境 Django 成功连接 RDS
- 能正常执行迁移
- 系统启动后，文章、术语库、日志等数据读取正常

---

# 7.4 OSS 媒体存储接入

## 目标
将正式图片与媒体资源迁移为 OSS 存储。

## 要求
1. 媒体上传与读取使用 OSS
2. 图片本地化流程最终产出 OSS URL
3. 封面图、正文图、媒体素材都可通过 OSS 正常访问
4. 文章表 / 媒体表中记录 OSS URL
5. 如当前系统存在本地 media 逻辑，需要兼容迁移或明确替换

## 范围说明
本轮只要求：
- 存储稳定
- URL 可用
- 与编辑器集成正常

不要求：
- 高级媒体管理
- 图片智能处理
- 去水印

## 验收标准
- 图片本地化后不依赖本机路径
- 前台文章中的图片可正常加载
- 封面图可正常展示

---

# 7.5 Nginx 与 HTTPS 配置

## 目标
为前台和后台提供稳定的 HTTPS 访问入口。

## 路由要求
- `/`：前台信息流与详情页
- `/admin/`：后台系统

## 要求
1. 配置 Nginx 反向代理
2. 正确转发到 Django Web 服务
3. 配置 HTTPS 证书接入方式
4. HTTP 自动跳转 HTTPS
5. 正确处理静态文件与媒体文件访问

## 验收标准
- 域名访问可成功打开前台首页
- `/admin/` 可正常登录后台
- 整站 HTTPS 可用

---

# 7.6 Celery / Redis 生产化部署

## 目标
确保抓取、翻译、推送任务能在生产环境稳定运行。

## 要求
1. Redis 作为 Celery broker / backend 正常运行
2. Worker 正常消费任务
3. Beat 正常触发定时任务
4. 任务失败有日志
5. 翻译、抓取、推送任务互不阻塞
6. 周期任务时区保持与当前业务逻辑一致

## 说明
- 当前业务时区仍按 `Asia/Shanghai` 处理
- 不要因为服务器部署在香港就改变任务业务时区逻辑

## 验收标准
- 定时抓取能按规则执行
- 自动翻译能正常执行
- 手动推送任务能进入队列并执行

---

# 7.7 日志、监控与告警

## 目标
让生产环境出现问题时可观测、可定位。

## 本轮最低要求
至少支持以下观测能力：

1. Web 服务运行状态
2. Celery Worker 运行状态
3. Celery Beat 运行状态
4. 最近一次抓取任务结果
5. 最近一次翻译任务结果
6. 最近一次推送任务结果
7. 应用错误日志输出

## 告警范围（最低要求）
至少应能发现：
- Web 无法启动
- Worker 无法启动
- Beat 无法启动
- 抓取任务持续失败
- 翻译任务持续失败
- 推送任务失败

## 实现说明
本轮不要求接入复杂观测平台，但至少要有：
- 容器日志可查看
- Django / Celery 日志可落盘或标准输出
- 有基础失败排查手段

## 验收标准
- 问题发生时能够快速定位到失败模块
- 抓取、翻译、推送失败不会静默消失

---

# 7.8 备份与恢复

## 目标
确保系统具备最小可行的数据安全能力。

## 必须准备的能力
1. 数据库备份方案
2. 媒体文件备份或可恢复策略
3. 环境变量与部署配置备份
4. 基础恢复说明文档

## 最低要求
- 数据库支持每日自动备份
- OSS 资源具备可追溯性
- 有一份恢复步骤文档

## 验收标准
- 出现数据问题时，可按文档执行恢复
- 至少完成一次恢复演练或恢复路径验证

---

## 目标
让部署过程可重复，出现问题时可回退。

## 必须交付
1. 部署脚本（如 `deploy.sh`）
2. 如有必要，补充更新脚本
3. 回滚说明文档
4. 环境变量模板文件
5. 生产部署 README

## 回滚要求
至少说明：
- 代码回滚怎么做
- 容器回滚怎么做
- 数据库恢复怎么做
- 媒体资源恢复怎么做

## 验收标准
- 部署步骤清晰可执行
- 至少具备最小回滚策略
